## 1. 这个分支负责什么？

AURA 的范围比 Embodied-AI 的广域前沿观察更窄：聚焦**自适应机器人操作智能（Adaptive Robotic Manipulation Intelligence）**。跟踪 VLA/VLM 操作系统、长程任务、状态与记忆、用于物理决策的世界模型、验证/失败诊断/恢复/学习、本体迁移、操作感知与物理交互、数据集/基准/仿真器/评估，以及有技术意义的实验室/公司/开源发布。

这不是原始新闻流，而是供研究与开发选择使用的持久记录。

上游为 [Embodied-AI Research Frontier Watch](https://github.com/NoctisBaguette/Embodied-AI-Research/tree/main/reports/frontier_watch)。预期流程是：周一广域扫描 → 周四 AURA 读取上游并独立搜索 → 用操作智能视角综合 → 提交研究和实验影响。

明确区分 **CONFIRMED（独立核实）**、**NEW（AURA 新发现）**、**DIFFERENT INTERPRETATION（不同解释）**、**NO ACTION（当前不行动）**。重复阅读上游摘要不是独立佐证。

研究标签为 **WATCH（观察）/ READ（阅读）/ DEEP DIVE（深入研究）/ REPRODUCE（复现候选）/ NO ACTION（不行动）**。它们是研究优先级，不是论文质量评分，不是开始执行的命令，也不代表复现已经完成。

## 2. 决策权限与执行保护

Frontier Watch 不因新论文出现就直接改写 `ARCHITECTURE.md` 或 `DECISION_LOG.md`。流程为：

```text
05 前沿观察
 → GitHub 研究材料
 → Core/02 评审
 → 有证据支持时形成架构/决策变更
 → 06 实现与实验
 → 结果回到 Core
```

**对领域的认识可以每周更新；已批准实验不应每周自动改变。**提出调整前，读当前 `ROADMAP.md`、Core 连续性记录、最新工程验收/授权。证据可能在实验分支而不在 main。使用当前命名与职责，保留历史 AETHER-CL 标识，不覆盖 Core/02W 审批关卡。

| 执行影响 | 含义 |
| --- | --- |
| MONITOR / BACKLOG（观察/待办） | 默认：保留来源与意义，不改变当前工作 |
| NEXT-CHECKPOINT CANDIDATE（下一检查点候选） | 可能解决已知瓶颈或提供重要对照，交 Core 在有边界的评审中选择 |
| IMMEDIATE REVIEW（立即评审） | 安全、无效测量/比较、依赖破损或决定性可行性问题；必须说明受影响的具体假设，由 Core/工程决定停或修 |

更新模型、排行榜变高或架构名称重叠，本身不足以打断有效实验。已有工作可要求收窄创新表述，但不使现有工具、基线或消融自动失去价值。

不得因前沿条目在研究中途修改任务、基线、数据划分/种子、干预、指标、资源预算。必要修正应有明确修订记录，并与冻结证据分开。正常设计变更留到约定里程碑。基础设施阻塞也不是从零重做架构的理由。

默认每位负责人只有一个活跃核心假设实验；独立且获批的硬件/工程工作可以并行。新增实验须写负责人、可测问题、基线、最小干预、资源、完成标准，以及它替代什么或为何有额外产能。HQ/Core 保留批准权。

每期报告结尾写清：**继续什么、现在改变什么、下一检查点的零或一个首选候选、暂缓什么、本次实际产生了哪一级证据。**“当前实验不变，继续”也是有价值的结论，但不能以此为由省略重要发现或实施选项。

## 3. 跨项目复用

Embodied-AI 的学习/模型/首个仿真器里程碑不是 AURA 的工程状态。兼容时共享冻结环境、适配器、协议和证据，不能让 AURA 重新回到首个仿真器选择，也不要跨项目重复完全相同实验。一个交付物有一个负责人；研究问题或评测条件不同才需要独立执行。

区分：作者结果、公开代码、已下载资产、本地测试、原生执行、独立审计。主要外部主张在进入架构证据前要回查一手来源。

## 4. GitHub 每次需要保留多少信息？

采用分层深度，不设固定字数：

1. **CURRENT：**当前决策摘要、最新工程背景、变化的优先级、未决事项、建议和详细资料链接。保持可导航，旧表和判断保留在日期报告/Git 历史。
2. **日期报告：**重要方法改了什么、为何与 AURA 有关、代表能力、证据/局限、可行比较；明确两项目差异，而非复制上游论文表。
3. **必要的证据详情：**一手链接/ID、核验日期和版本、指标及比较条件、资产状态、兼容性/资源限制、未核实部分，区分同名系统。
4. **可行动的决策/团队详情：**选项、推荐、前提、具体交付物、验收条件、评审者、明确标为估计的工时、排除范围、下一授权关卡。

只有“论文名 + 分数 + DEEP DIVE”不够交接。接手者必须能回答：**改变了什么？依据是什么？还有什么方案？要做/测什么？成本如何？何时算完成？谁需要决定？**

不复制整篇论文或全部聊天；保留形成决策所需的推理与证据，附深层来源，不能压缩掉关键局限。

## 5. 团队协作与决策记录

每个工作包必须写具体问题及其服务的决策、带路径/分支/来源的输入、交付物和建议位置、可检验验收条件、依赖/资源/工时估计、角色/评审者/状态/排除范围，并区分准备、实现、原生执行和接受。

保护一个实验不等于整个团队只能等待。独立获批工作可以并行：HQ 决定产能与顺序，Core 决定科学范围，06 控制集成与原生证据。写出文档不等于已经分配队友、任务已接受或其他聊天已收到通知。

使用本包局部 FW ID，不凭空新增全局 DEC ID。真正评审后记录批准/暂缓/拒绝、日期、批准者、理由、负责人和证据；保留旧选项与失败。架构决定仍由 Core 写入正式记录。

## 6. 中英文同步规则

英文继续供用户和主要研究文档使用；团队交接另有简体中文版，不替换英文。中文必须包含理解任务所需的背景、两份观察变化、机制和意义、来源/证据局限、选项与待决事项，以及完整工作包。无需全文翻译外部论文，但不能只有中文标题加英文链接。

两种语言保持相同问题、输入、交付物、验收标准、依赖、工时、评审角色、排除范围和审批状态。模型/论文名、代码标识、路径、命令、链接和 ID 不变；重要术语首次出现可保留英文。不得把拟议改成已批准、删去不确定性，或改变数值阈值。

采用独立文件（`.zh-CN.md`），通过本索引与各文件顶部互相导航。中文文件记录对应英文内容 blob 和译制日期。范围、证据、验收或决策有实质变化时同步两种语言；若不同步，明确标为过期，不能假称一致。

**阅读顺序：**当前雷达 → 最新简报及所需证据/团队附件 → 趋势台账 → 只有需要溯源时才读更旧报告。
