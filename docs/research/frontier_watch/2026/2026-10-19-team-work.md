## WP2 — Sensor/evidence interface and fixture checks

**Proposed owner:** sensing/software teammate; **review:** 06-01 for compatibility, Core for semantics. **State:** unassigned, proposed preparation.

**Decision served:** D1 — make existing sensor commissioning/review easier to finish; prepare D2 without changing experiment conditions.

**Question:** Can we represent observation validity and provenance without leaking simulator answers or interpreting absent evidence as failure?

**Inputs:** branch files `AURA_M9a_Commissioning_Start_v0.1.md` and `AURA_M9a_Camera_IO_Commissioning_v0.1.md`; the accepted M8/M9a input boundary; representative allowed packet/schema examples from the engineering owner. Do not invent a new native API.

**Deliverable:** a field-level contract and, if approved for a separate preparation branch, fixture tests. Proposed review note: `docs/research/coordination/team_returns/FW-20261019-WP2.md`. Final code path belongs to 06, not this report.

**Minimum fields to assess, not automatically add:** observation timestamp, arrival timestamp, sensor identity/calibration, measured robot state, evidence validity, effect identifier and permitted command context. A proposed record distinguishes observed truth/falsity, unknown evidence and not-yet-due pending conditions. Units, coordinate frames and time domains must be explicit.

**Done when:**

- There is a schema mapping to existing packets, with forbidden truth/contact/reward/condition/evaluator fields identified.
- Fixtures cover valid observations, missing data, stale timestamps, out-of-order delivery and actual contradictory evidence.
- Tests do not substitute a command's intended effect or a generated memory sentence for a measured physical outcome.
- Any proposed behavior differs from the accepted interface only in a separately listed, unapproved change; the current executor and recovery rules remain untouched.
- The return labels exactly what was inspected versus actually tested. Synthetic fixture success is not native camera neutrality or verification accuracy.

**Estimated effort:** 4–8 focused hours after receiving the real packet examples. **Dependencies:** packet/schema access; 06 agrees the preparation branch and test scope. CPU fixtures may be possible; native GPU work is not part of this assignment.

**Excluded:** changing sensor thresholds to improve scores, new environment resets, new force conditions, policy replacement, new recovery behavior, fresh M9 evaluation or edits to frozen execution code.

## WP4 — Failure/evidence annotation and evaluation specification

**Proposed owner:** evaluation/data teammate; **review:** 06 evidence reviewer and Core/02. **State:** unassigned, proposed.

**Decision served:** D1/D2 — produce evaluation material that distinguishes sensing problems from physical and task-level failures.

**Inputs:** allowed retained camera/episode evidence supplied by the engineering owner, existing scoring definitions, E7 LABIT's dependency perspective, and the evidence limitations in this packet. Anvil remains an optional primary-review lead, not a required model.

**Deliverable:** annotation guide, small reviewed sample when actual footage is available, and metric schema. Proposed path: `docs/research/coordination/team_returns/FW-20261019-WP4.md` plus a linked non-sensitive manifest.

**Labels to distinguish:** observed effect achieved; observed effect violated; insufficient evidence/occlusion; evidence stale; intended action not yet due; previous condition invalidated; false declaration of task completion. Record evidence time and decision time separately. Do not label an unseen state by intuition.

**Done when:**

- Each label has an operational rule and example; inferred cause is separated from directly observed effect.
- A small sample is independently reviewed and disagreements recorded. If data is unavailable, deliver a schema and explicitly synthetic examples, not a claimed labeled native dataset.
- Privileged reference labels, scene/seed identifiers and condition labels are evaluator-only and cannot enter deployment inputs.
- The metric plan includes coverage/unknown rate, false success, false intervention, detection delay and end-to-end latency; task success and controller completion remain separate.
- Calibration/development/evaluation boundaries and manifest/hash provenance are specified before expanding the sample.

**Estimated effort:** 3–6 focused hours after obtaining usable evidence. **Dependencies:** actual frame/log availability and authority to access/share it; no new collection campaign or hardware purchase in scope.

**Excluded:** changing old labels silently, fabricating hidden physical facts, relabeling screenshots as full rollout evidence, tuning on future evaluation scenes, or collecting fresh experimental seeds without approval.

## 3. Later optional package — action-aware retrieval

Do not activate merely because Robota-Embed is interesting. Prerequisites are a consistent episode/action schema, a usable corpus with permitted access, an available retrieval model or explicit simpler baseline, and an agreed downstream consumer.

A first task would be offline retrieval with held-out episodes and queries that contain only information available at decision time. Final policy success and cross-task improvement require later experiments. This is a backlog option, not a fifth current assignment.

## 4. Integration: how the pieces become development

WP1 returns the smallest decision worth testing. WP2 returns a compatible evidence interface/test boundary. WP4 returns a way to measure it. WP3 may establish an independent future learned baseline without blocking the present fixed-controller study.

Core should combine only the accepted pieces into one bounded protocol. Before a new native comparison, the protocol must state hypothesis, task, unchanged baseline, changed mechanism, inputs and privilege, data splits/seeds, metrics, resource budget, stop conditions and exact evidence artifacts. Approval and execution are different events; both must be recorded.

Prefer a short integration review at the agreed milestone over requiring everyone to finish every paper. A negative feasibility result or an experiment that rejects the hypothesis is a valid return.

## 6. Required teammate return format

Each return should contain:

1. Assigned question and scope, actual owner, reviewer and status.
2. Inputs and exact source/code/data versions used.
3. What was changed or inspected, and what stayed fixed.
4. Delivered artifacts with paths/commits.
5. Checks actually executed, raw evidence and failures; clearly label planned tests.
6. Result, uncertainty, limitations and rejected alternatives.
7. A concrete recommendation: integrate, perform one further named check, defer, or stop.

The review is complete only when another person/chat can trace the claim to an artifact and understand what decision it supports. This is the information standard that makes GitHub a collaboration workspace rather than a paper list.
