# AURA 研究协作工作台与开放技术路线组合：提案

日期：2026-11-12。状态：**提交用户 / HQ / Core 评审的提案**，不是已批准的架构、平台采购、成员分工或实验授权。

[English companion / 英文配套](AURA_Research_Workbench_Proposal_2026-11-12.md)

## 1. 建议

保持**研究目标稳定，同时允许技术实现接受比较与替换**。AURA 应研究资源可承受、可靠的操作能力迁移，而不是把项目身份绑定在某一种策略、世界模型、记忆结构或验证外层机制上。保护正在进行的实验范围，不等于把整个团队的探索限制在该实验内。

建立共享的**从研究到开发的协作工作台（research-to-development workbench）**，而不是再增加一个按日期排列的论文档案。它应连接外部证据、候选机制、AURA 已有能力、不同系统配置、实验和决策。队友应能直接回答：**这个方法能帮助我们做什么？哪些结论有证据？还有什么不清楚？完成哪一个小任务就能减少这种不确定性？**

建议顺序：先用现成的协作型关联数据库做试点；GitHub 继续保存代码与已接受的证据；只有试点暴露出明确不足时，再开发轻量的自定义比较界面。对中文优先的团队工作区，飞书多维表格是首个候选；如果团队已有 Notion 使用习惯、访问条件更好，或其可用的 ChatGPT 集成更方便，Notion 可作为替代。正式选型前必须实际检查访问、权限、导出和集成。本文没有选定或部署任何平台。

## 2. 项目背景与边界

本次读取的当前架构已经说明：模型是可替换能力，表示可采用显式、学习式、潜变量或混合形式，对物体、任务、环境、本体和经验的迁移是核心研究对象 [P1]。路线图同时保留实体抓取/软抓取分支和受控仿真研究 [P2]。

Core 连续性记录 v0.2 规定了 M9a 的有限调试路线，以及新正式评估前独立的 Core 验收关卡 [P3]。本提案不改变这些要求，也不核实当前服务器健康状态、不覆盖操作者的暂停决定。历史 AETHER-CL 标识保留；公开身份为 AURA，BAGUETTE 仍是暂定的内部 Core 名称。

本次读取的最新研究雷达是11月5日更新 [P4]。其中的来源清单只是背景，不意味着本文重新核查了所有相关论文。

## 3. AURA 可以在哪里创造价值

一个值得讨论的候选研究主张是：**在目标域数据、工程投入和算力有限时，使操作能力更容易迁移、组合与部署。**

贡献不一定是重新预训练一个基础模型。只要问题明确且证据充分，小机制、可靠集成、受控评估协议，或对一种失败的解释都可能有价值。反过来，仅把现有 API 接起来或减小模型体积，也不能自动证明科学创新或可靠迁移。

每个迁移提案需要记录：

| 要素 | 必须说明什么 |
| --- | --- |
| 源条件与目标条件 | 哪些物体、环境、传感器、机器人/动作接口、数据分布或计算设备发生变化？ |
| 保持不变的部分 | 视研究问题说明策略权重、任务、验证器、控制器、预算和训练数据等固定项 |
| 允许的适配 | 零样本、标定、示范、适配器训练、微调或代码修改 |
| 成本 | 目标域数据、GPU 时间、集成/标定工作量、内存、时延和干预成本 |
| 证据 | 保留的目标域测试条件、干净/源域结果、不确定性、失败与退化 |

数据格式转换、数据域迁移、本体迁移和策略后端可移植性是不同的主张。统一接口不能证明策略能够适应新机器人。压缩/部署研究应衡量源域和目标域上的可靠性—资源权衡，而不只是权重文件大小或平均推理时间。

## 4. 将接口模块化，而不是把假设固定下来

区分三种模块化：

- **功能层面：**可以分别讨论感知、状态/历史、动作、验证和恢复。
- **软件层面：**可以通过明确接口调用组件。
- **学习表示层面：**独立替换经过训练的内部组件而不损失性能。

前两者不能证明第三者。如果一个模型内部是联合训练的，应允许把它整体视为一个模块。显式状态、潜变量上下文，以及不增加额外记忆的基线都应是候选。通用符号本体或在线世界模型不是先决条件。

策略适配器协议应明确：观测模态、预处理/归一化、状态/历史需求、动作表示与单位、坐标系、相对/绝对动作约定、动作块时长、控制频率、重置/会话语义、模型版本，以及缺失/过时输入的处理方式。独立的机器人适配器负责支持的执行接口与运行限制。不支持的组合应明确拒绝，而不是悄悄转换。

在兼容时复用已有基础。LeRobot 文档描述可组合的观测/动作处理器 [S1]；openpi 文档描述远程策略服务和轻量机器人端客户端 [S2]。它们是实现参考，不是替换 AURA 当前环境的命令，也不证明普遍兼容。

### 用于讨论的路线配置，不是已批准实验

| 配置 | 组合 | 用于检验什么 |
| --- | --- | --- |
| R-A：显式监督路线 | 兼容的控制器/策略 + 几何/任务状态 + 时序结果检查 + 有界恢复 | 小型显式机制能否提高分布变化下的可靠性？ |
| R-B：整合式学习路线 | 预训练时序/潜状态策略 + 必要运行约束；不强制增加外部记忆或世界模型 | 更简单的整合模型能否达到要求的可靠性与成本？ |
| R-C：高效适配路线 | 兼容的预训练策略 + 经标定的传感/动作适配器 + 一种压缩或轻量适配机制 | 能否以更低算力或适配成本保留目标能力？ |

不要同时训练全部路线，也不要穷举所有组合。选择少量有意义的替代方案并分阶段消融。工作台必须显示不兼容和未经测试的组合，而不只是漂亮的架构图。

## 5. 信息结构：可复用记录，而不是每周重复复制

使用稳定 ID 和带类型的关联。周报是这些记录的一种视图，而不是记录的唯一归宿。

| 记录类别 | 最少需要的有效信息 |
| --- | --- |
| 来源与主张 | 论文/模型/数据集/仓库身份及版本、带日期的原始链接、机制摘要、证据与局限、产物就绪状态、首次/最近检查、两份周报的来源关系、人工修正 |
| 能力与模块 | 目的、输入/输出、假设、需求、实现/参考链接、兼容性、证据状态 |
| 候选系统 | 具体模块版本、兼容接口、目标场景、估计资源范围、替代方案和未解决风险 |
| 实验与结果 | 问题、基线/处理组、源域/目标域划分、固定变量、适配预算、协议/提交、实际凭据、结果与失败案例 |
| 决策与工作 | 选项、理由、批准/状态、负责人/评审者、有边界的交付物、依赖、验收标准和下次复审触发条件 |

一个方法可以包含证据强度不同的多项主张。区分作者测量、可访问产物、已检查代码、本地测试、原生执行和已接受审计结果。未知不等于失败；未报告不等于不支持；未调查不等于不存在。

每个来源保留两层判断：**该工作本身声称解决什么**，以及 **AURA 当前如何理解它的相关性**。第二层可以随研究问题变化。在当前狭窄筛选范围之外保留来源信息，但不要把每一项都升级成深读或任务。

## 6. 面向使用者的界面

### A. 研究库 / 发现收件箱

提供可搜索的可视化卡片：简短中文摘要、英文切换、来源身份、机制、能力标签、产物状态、局限、最近检查、评审者和链接。队友可直接提交网址、短评、图片或视频引用，不必先填写长表单。AI 辅助提取生成的是草稿，而非已核实事实。

### B. 能力比较

选择任务状态维护、相机域适配等能力，把相关外部方法和**我们自己的具体实现版本**并排比较。比较行包括输入特权、动作接口、训练需求、记忆、时延、已演示迁移、恢复和可用性。每个单元格都可以打开证据及其条件。不同基准上的数字不能直接排榜。不要把比较简化为没有来源的绿色勾选或星级。

### C. 候选系统配置

通过易读的配置表显示模块选项、依赖、不兼容接口、算力假设和哪些组件可省略。以后可用小型自定义并排界面改善这一部分。第一版不需要拖拽架构编辑器或实验执行编排器。

### D. 实验与决策队列

分别显示拟议问题、已批准协议、受阻运行、返回证据和已形成决策。论文被标为 READ 或 REPRODUCE 不等于已批准任务。每个实验提案应写清：结果会改变哪个决定，以及什么结果会反对该假设。

### E. 我的任务 / 会议视图

队友能看到获分配的问题、必要阅读、准确交付物、评审者和完成标准。会议视图显示变化内容、两三个相关替代方案、待决事项、不同意见和下一项证据需求。可以直接围绕这个视图进行简短轻量讨论，不强制制作展示型 PPT。

## 7. 一次示例交互

示例问题，尚未批准实验：**更便宜的相机配置能否在变化后的工作区保留可靠放置能力？**

团队打开这个迁移问题，选择两三个传感/策略配置，把原始证据和我们自己的能力状态放在一起看。一名成员检查标定/接口兼容性，另一名评估小规模模型适配选项，另一名准备目标场景标签和失败指标。这是互补且有边界的交付物，不是固定部门。

最终可以决定保留原系统、开展小型适配器研究，或排除成本过高的路线。决策关联它依赖的证据和受影响的实验。否定某条路线的结果仍然有用。下一次前沿观察便能提示真正相关的新方法，而不必重新打开无关决定。

## 8. 可靠更新与向 AI 聊天分享

建议更新流程：两份前沿观察和队友提交 → 规范来源 ID/版本匹配 → AI 草稿字段 → 对重大内容人工核查 → 关联记录与视图 → 带版本的决策快照。

按论文/模型/仓库身份及修订去重，不只按标题。保留两个项目对同一来源的不同判断，不把它们制造成两份独立实验证据。修订更新已有记录，并显示变更历史；不能覆盖人工笔记、已接受决策或执行状态。

明确字段归属：

| 权威来源 | 负责内容 |
| --- | --- |
| 协作工作区 | 收件、来源卡片草稿、工作中的比较、讨论和未批准研究问题 |
| 已启用时的 GitHub 工程 Issues/PRs | 实现负责人/状态与代码评审；工作区引用这些信息，而不是再维护一份冲突状态 |
| 版本化仓库证据 | 由原有负责人维护的已批准协议、代码、实验凭据和已接受决策 |

先实现受控导入和带版本导出，不一开始就做复杂双向同步。后续 API 集成需要认证、权限范围、冲突检测、稳定记录 ID、重试和审计日志。记录更新不能自动提高证据级别。

**导出讨论包**应以 Markdown 加结构化 JSON 保留：选中的记录 ID、来源版本/链接、中英摘要、比较配置、当前 AURA 修订/范围、替代方案、未决问题、决策和证据清单。即使没有实时平台权限，HQ/02 或其他 AI 也能据此获得有效上下文。仅导出 CSV 可能丢失关联语义，应显式导出外部 ID 并测试恢复 [S6]。大体积原始视频/日志保留在权限适当的存储中，记录哈希和位置，不反复复制进每个讨论包。

观察/导入任务失败时，应显示最近成功更新时间和缺失覆盖。明确的失败或过期标记，优于看似最新但实际上不完整的工作区。本提案没有创建自动刷新服务。

## 9. 平台选择

| 选项 | 已核查的有效功能 | 主要权衡 / 判断 |
| --- | --- | --- |
| 飞书多维表格 + 文档 | 画册/表格/看板、关联记录、表单、协作/权限功能以及记录 API [S3,S4] | 中文优先团队交互的首个试点候选。账号访问、配额、权限和认证导出需要实际测试；此处未连接 |
| Notion 数据库 | 画册、关联、评论和 Markdown/CSV 导出 [S5,S6] | 如果团队访问/使用更方便，是合理选择。本次发现了可接入的 Notion 集成，但尚未连接。导出时需明确保留关联 |
| GitHub Issues/Projects | 与代码关联的任务、表格/看板/路线图、自定义元数据和自动化 [S7] | 适合工程执行证据，但不宜作为唯一的可视化研究比较界面 |
| 完全自建应用 | 可实现本文设想的准确比较/配置交互 | 我们必须负责认证、权限、协作、编辑、存储和维护。不建议从这里起步 |

**拟议选型：**用一个现成协作工具做试点，GitHub 继续作为证据与代码基础。只选择一个协作工具，不要同时堆叠飞书、Notion 和另一个任务系统。初期自建范围限制在导入/导出校验，以及确有需要时的轻量比较查看器。

不要把静态可视化原型误认为共享应用：浏览器本地修改不等于团队共享持久化。GitHub Pages 是静态托管，公开发布也可能暴露来自私有源仓库的材料 [S8]。公共文献层与团队私密层应分开；后者包含内部笔记、未发布结果、预算和访问细节。不能在客户端页面中嵌入凭据。当前仓库公开，也不代表同意公开今后的全部团队材料。

## 10. 试点范围与验收

建议试点包含：现有观察中约15–25条有代表性的来源记录、三种候选配置、两三个真实项目瓶颈、一个真实已有实验记录，以及少量可选择工作包。这些是设计目标，不是已经导入的内容。需包含挑战当前路线的方法，以及至少一个尚不可用或不兼容的产物。

只有队友能完成以下操作时，试点才通过：

1. 无须编辑 Markdown 就能提交来源，并避免生成重复记录。
2. 找到相关方法，依据证据解释两个替代方案的差别。
3. 分清公开主张与 AURA 自己的实测结果。
4. 找到自己的实际任务，理解完成标准。
5. 记录决策、不同意见和以后复审的触发条件，而不是悄悄改写历史。
6. 再次导入或更新周报时，不丢失人工注释、不凭空新增任务。
7. 导出并重新打开 AI 可读讨论包，保留关联、版本和双语含义。
8. 用无权限账号或退出登录状态证明预期访问限制有效。

如果维护平台开始挤占操作智能研究，就停止扩张。如果真实会议后发现现成视图已经够用，就不开发自建应用。如果某种明确比较反复造成困难，只补这个缺失交互。

## 11. 治理与下一决定

HQ 负责平台采用、团队访问、范围与资源分配。Core/02 负责科学比较和被接受的研究方向。05 负责带证据链接的候选记录及更新；06 负责工程证据和运行集成。可用一个有边界的工作台设计/实现聊天负责试点，不让它接管 Core 或前沿观察。

建议角色包括来源整理、传感/接口、模型/部署可行性、评估。可以结合已有专长，但不是刚性分工。负责人应负责一个问题或交付物，而不是永久被限制在某个模块内。本文未分配任何人员。

**待决事项：**接受或修改工作台概念；完成访问/导出检查后选择试点协作平台；指定负责人并冻结试点边界。批准工作台不等于批准新的机器人实验。
