24日12:00：检查就绪状态，计划冻结checkpoint。candidate证据未完成或没有更好时，由队长评估已验证fallback。只冻结身份明确且已测试的策略；截止不会让弱模型或未验证模型自动合格。必要修复形成新身份并做对应复验。停止可选功能。
24日20:00：最终交模型包/代码/配置、真实结果与覆盖清单、复现说明、验证证据及未解决阻塞。这是本计划使用的团队内部硬截止；正式提交由队长另行执行。

这是一套在两人现在开工、及时获得输入与资源时可执行的实现分工，不保证模型效果、原生稳定性或全量评测覆盖。队长指定内部完成日为24日，20:00是本计划的明确安排，不修改主办方规则/正式截止，也不把必做项留到25/26日。

模型效果决策由队长负责
不要等到24日才看第一段失败视频。现在复盘baseline；用A的一致性检查定位或排除具体打包/输入缺陷；保持当前candidate流程运行。完成后比较相同面板的成功数、行为、退化与基础设施错误。保留fallback，不凭loss较低或更新更多选模型。确证具体bug时，准备一次针对性修复和有身份记录的复测，不做猜测性升级或最后一刻大范围超参搜索。冻结时仍无可接受的已验证模型，就如实记录交付/效果风险，由队长决定正式提交操作。打包本身不能修复差的策略行为。

6. 日报：22日、23日每天交，24日交最终报告

被卡住或没写完也交简短报告。允许AI起草，本人核对实际文件/日志。22/23日22:00前日报，23日12:00另交代码草稿；24日12:00报就绪情况，20:00交最终报告与代码。收到时已过节点，阅读后两小时内先报起始状态及实际可用时间。关键阻塞发现就说，不等晚间日报。

建议约 400–800 个中文字，证据另附。直接复制填写：

日期/时间（北京时间）：
姓名 / 角色 A 或 B：
交付判断：按计划 / 有延期风险 / 被阻塞 —— 原因。
1）完成项：现在具体能做什么；每项给修改文件/commit/输出。未实现则说明检查或尝试了什么。
2）验证：检查 → PASSED / FAILED / NOT RUN → 准确命令 + 真实日志/结果。区分 CPU 样例与真实权重/GPU/仿真运行。
3）剩余：逐项写必须完成的工作，状态为未开始 / 进行中 / 已实现未验证 / 已验证。未完成项估剩余动手工时（可给范围）；GPU 执行与等待外部资源另列，不知道就写 UNKNOWN。
4）阻塞：准确需要的输入/权限/决定、谁提供、最晚何时要、等待时能继续什么。
5）下一份交付：具体文件/行为 + 预计北京时间；23日草稿及24日最终交付能否赶上？不能就说明现在需要转交什么。
6）接手：最新 commit/ZIP、启动命令、已知失败、第一个未完成步骤、建议转交工作和剩余工时。职责转交须和队长确认。
7）附件：修改代码/补丁或 commit；真实检查/日志；缺失输入清单。

A 必须覆盖清单、导出、加载、入口、新进程一致性状态，写明缺哪些权重/参考输入。B 必须覆盖 100 组合计划、记录/续跑/汇总、与 A 联调、真实 episode 数和实测吞吐。只跑 fixtures 时，真实 episode 写 0。

23日中午即使未完成也交当前代码、准确命令和按优先级排列的剩余必做项，队长可在下午及24日整合补齐。24日附最终已验证/未验证清单、可复现的模型包/结果身份。日报不能代替实现。

给 AI 的日报提示词：“根据我实际文件、命令、日志和可用时间，填写上述日报。不编造进度、测试、工时或百分比。区分已实现未验证与已验证、CPU 样例与原生执行、动手与等待。明确阻塞、下一份交付和接手步骤；只询问准确报告所缺事实。不能读取的证据注明是我提供的情况。”

7. GitHub 或直接发文件，二选一即可

GitHub 方便协作，但不是开工和日报的前提。整合分支是 lingbot/competition，不是默认 main；main 上还有其他 AURA 工作，别改不相关实验。

  commit 后把 PR/commit 链接发给队长。未合并报告在 PR 中可见，队长审查合并后更新共享进度；不能默认个人分支报告已出现在整合分支页面。

分支存在不代表你自动获得写权限。没有权限时，熟悉 fork/PR 就用它，否则直接交文件，不要为 Git 配置浪费一天。

直接交接方式：

仓库是公开的：公开日报放脱敏摘要、代码身份和非敏感输出。不要提交 SSH 凭据、个人服务器地址/路径、私有原始日志/事故记录、模型权重或数据集。GitHub 不会自动部署到正在运行的服务器，也不会自动监控它。队长的助手在收到请求后审查更新；commit 本身不会触发审查或提醒。
