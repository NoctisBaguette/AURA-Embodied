1. 我们在做什么

我们参加 LingBot-VLA 2.0 比赛的 RoboTwin 仿真赛道。策略模型读取三路相机图像、机器人的关节/夹爪状态和任务指令，输出机器人动作。训练使用规定的 Aloha-AgileX 50 个任务的 clean 示范数据。最后要提交相互匹配的模型权重、可运行代码、评测结果和复现说明。

官方完整评测范围是 50 个任务 × clean/randomized 两种设置 × 每种组合 100 次，共 10,000 次。当前流程中的 32 次基线和 32 次候选模型评测是小规模对比，不等于完整评测。

现在并行推进三项工作：
- 队长 Baguette + 当前助手：操作现有服务器流程、检查运行证据、选择 checkpoint、整合提交。
- A：模型导出、独立加载和复现代码打包。
- B：完整评测、断点续跑和准确的结果统计。

这是两项实际的工程开发任务，不要求再设计一个模型，也不要求另开一轮训练实验。

给 AI 的方式：
- 上传 ZIP，再粘贴 02-AI-PROMPT-A.txt 或 03-AI-PROMPT-B.txt 中任一语言的提示词。
- 先要求 AI 列出实际读到的文件，并指出真实的保存/加载或结果生成/消费函数，再提出修改。

4. A — 模型独立加载和复现入口

目标：别人用一个新进程，按说明加载出同一个训练后的策略，不依赖旧实验目录或队长的个人主目录。

开始做什么：
1）检查 joint50_train.py 的 checkpoint 保存/恢复、model_core.py 的模型状态和 joint50_policy.py 的推理流程，记录实际保存和消费的状态。
2）列出基础模型版本、adapter、五个训练过的投影模块、持久 buffer/模型 step、tokenizer/processor/配置、clean50 归一化参数，以及预处理和推理设置。只保存 adapter 不完整。
3）在新的 submission 文件中实现可配置的导出/加载工具。检查必要文件及一致性，缺失或不匹配时明确失败。CPU dry-run 不能声称已经加载了模型。
4）整理 README.md、train.sh、eval.sh、configs/、src/。train.sh 对应真实的 clean50 训练流程和来源；eval.sh 调用 B 的评测程序。

当前联合训练代码保存的格式包括 adapter_model.safetensors、projection_weights.safetensors、adapter_config.json、resume-state.pt、norm-stats-clean50.json 和 checkpoint.json。已有备用 checkpoint 的格式必须单独检查，不能默认完全相同。源码 ZIP 没有实际 checkpoint 目录，也没有固定输入/噪声张量。

由队长统一安排的 GPU 验证：
- 可以先使用已有 checkpoint，不必等待新训练完成。
- 导出后用新进程加载，检查具名张量、buffer 和 step 是否准确恢复。
- 在相同固定输入和噪声下，与原加载方式比较输出：归一化输出 (1,50,55)，解码后动作 (50,14)。记录实际误差和采用的容差，不能虚构“一致”。
- 推理加载不能依赖训练图片或历史运行目录；明确所有仍需外部提供的推理资源。

第一版目标：分工后约四小时交一个可审查的 CPU 初稿，包括文件清单、目录、CLI 和已完成检查。这不代表四小时完成最终 GPU 验收。

最终交付：导出/加载代码、manifest 和锁定的依赖、可运行的入口/配置/README、新进程加载及输出对比证据、明确的外部资源清单。A 负责打包加载，不另做一套评测实现。

5. B — 完整评测和可信统计

目标：一个固定策略覆盖全部 100 个任务/设置组合，支持正确续跑，输出能追溯到每次试验的官方统计。

开始做什么：
1）阅读 official/results-template.json、joint50_common.py、joint50_sim.py 和 manager.py，理解真实 episode 如何结束、父流程如何验收。
2）实现不使用 GPU 的 dry-run，覆盖恰好 100 个组合，记录任务、设置、目标次数、拟定种子、分片/输出位置和模型内容标识。每个组合的目标都是 100 次。
3）在新 submission runner 中参数化任务和次数。现有 pilot 固定两次评测，并限制候选种子数量；必须检查这些假设，不能简单重复启动原程序。
4）实现不可覆盖的逐次记录及安全续跑，防止重复计数、冲突记录和不同 checkpoint 混用。区分已完成的策略失败、无效场景拒绝和基础设施致命错误。
5）仅将真实完成的模型评测汇总到官方 results 格式，另存完成进度、错误和剩余队列。未完成组合保留实际次数；模拟器调试验收和人工测试样例不计分。

验证要求：
- CPU 检查覆盖成功/失败、重复及冲突记录、混合模型标识、非法计数、部分完成/错误记录、未知任务或设置，以及排除调试验收/测试样例。
- 接上 A 的加载器后，在统一安排的 GPU 时间里完成一组小规模真实评测和受控中断/恢复测试。
- 测量包括模型加载、场景准备和推理在内的真实速度，再估算全量剩余时间及资源需求。调试验收的耗时不能当作模型评测速度。
- 保留官方成功判定、任务动作上限和现有模型输入输出语义。种子预算或评测器改动须与队长审查并说明。

第一版目标：分工后约四小时交 100 组合 dry-run、汇总/校验代码和续跑设计。真实 10,000 次评测是之后的计算任务，不是今天初稿的完成条件。

最终交付：runner/配置、dry-run manifest、校验及有意义的测试、有真实记录后生成的 results.json、覆盖率/错误记录和复现命令。报告链接必须对应实际文件。最终分数不能拼接每个任务表现最好的不同 checkpoint。

6. 对接接口与依赖关系

开始编码前确认 INTERFACES.md。里面的 CLI 名称是拟定接口，不是 ZIP 中已经实现好的命令。

A 提供模型包和经过验证的加载器；B 的 evaluate 接收这个包；A 的 eval.sh 调用 B 的 evaluator。每条评测记录都标识模型内容 manifest，不能只记录一个可被覆盖的路径。

现有推理输入是三张 RGB 图像（240×320×3，uint8）、14 维 float32 状态和任务指令。预处理映射到 55 维。保持现有 50 步动作块、10 次去噪迭代、FP32 和零填充行为；本次分工不授权改变策略。

A/B 可以按照接口独立开发。B 可用明确标注的 CPU 测试样例检查连接，但这不能证明模型或仿真器正确。真实联调需要可用的加载器、确定的 checkpoint 和统一安排的 GPU。

建议分支为 lingbot/portable-package 和 lingbot/full-evaluation，在新路径开发。reference/runtime/ 保持不变。不要升级正在使用的环境、替换规划器、占用当前训练 GPU 或改服务器活动版本。如果确需修改接口，提交明确原因和补丁供审查。

7. 队长接下来继续做什么

现有流程独立运行：模拟器调试验收 → 32 次基线 → 联合续训（最多 100,000 样本 / 训练循环上限 22 小时）→ 32 次候选评测。这是计划和上限，不是预计完成时间或完成保证。

队长审查证据，选择一个可复现的 checkpoint，不会自动选用新候选模型。已有 clean50 模型保留为备用候选，也必须通过导出、加载和评测检查，其完整赛题成绩尚未建立。

队长提供明确缺失的 checkpoint 元数据/权重/参考输入，安排 GPU，审查队友补丁，整合 A+B，并负责实际提交。只有两位队友时，B 协助整理报告中的评测部分，A 提供加载/训练细节。每次同步说清：文件或 commit、已做检查、具体阻塞和需要队长给什么。

内部计划目标：10 月 21 日 CPU 初稿；22 日首次加载/评测联调；23 日中午前决定最终模型；23–25 日评测与打包；25 日 20:00 前准备好提交材料。目标取决于实际进度和算力。官方截止为 26 日 24:00 北京时间，实际提交前复核最新公告。
